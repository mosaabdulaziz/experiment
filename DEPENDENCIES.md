# Dependencies: locks and pins

Every Python environment is installed from a committed `uv.lock`, and every image and external source is pinned, so a
clean checkout builds the same thing tomorrow as today and an update is a reviewed diff. What ran before the pins is in
`deps/baseline/` (README.md there).

| environment | declared in | lock |
|---|---|---|
| sidecar image (`slim`, `mtmc`) | `perception/engine/requirements.txt`, `perception/modules/<name>/requirements.txt` | `perception/uv.lock` |
| app image, tests, dev, tools | `pyproject.toml` (groups `app`, `app-image`, `test`, `dev`, `data`, `tools`, `safety`) | `uv.lock` |
| attendance, barber, fall_detection | `products/<name>/pyproject.toml` | `products/<name>/uv.lock` |
| the seg model's ONNX export (`just barber-seg-model`) | `tools/onnx-export/pyproject.toml` | `tools/onnx-export/uv.lock` |
| the mtmc/ research tools (CUDA torch, as the sidecar) | `tools/mtmc-research/pyproject.toml` | `tools/mtmc-research/uv.lock` |
| the central MLflow server (`tools/mlflow-server`, Python 3.12) | `tools/mlflow-server/pyproject.toml` | `tools/mlflow-server/uv.lock` |

## uv

One uv minor everywhere: **0.13**. Each `pyproject.toml` says `required-version = ">=0.13.6,<0.14"`: any 0.13 release
from 0.13.6 on writes the same lock format, while another minor refuses to lock or sync instead of silently rewriting
the lock in its own format (0.13 writes new locks as `revision = 5`, 0.12 as `revision = 3`). What builds and checks
the repo is pinned exactly to **0.13.6**: the Dockerfiles copy uv from `ghcr.io/astral-sh/uv:0.13.6` pinned by
digest, CI installs `uv==0.13.6`, and so does Renovate (`constraints` in `renovate.json5`).

### Upgrading your uv

With a uv older than 0.13.6, or 0.14 and later, every `uv sync`, `uv run` or `uv lock` in this repo (and so `just up`,
`just check`, `just bootstrap`, ...) stops with

    error: Required uv version `>=0.13.6, <0.14` does not match the running version `0.12.10`

Any 0.13 from 0.13.6 on works; to match CI exactly, switch to 0.13.6, then rerun:

```bash
uv self update 0.13.6          # a uv installed with the standalone installer
pip install uv==0.13.6         # a uv installed with pip / pipx (pipx install --force uv==0.13.6)
```

Moving the repo to another uv minor is one change in all of the places above (the `required-version` range, the
Dockerfiles' image and digest, CI, `renovate.json5`, `tests/test_locks.py`), in its own merge request.

## The sidecar's lock

A module still declares what it imports in its own `requirements.txt` (`tests/test_module_requirements.py` checks it).
`perception/pyproject.toml` has one dependency group per requirements file (`engine`, `module-<name>`) and one per image
target (`slim` = engine + the Dockerfile's `BASE_MODULES`, `mtmc` = slim + `MTMC_MODULES` + CUDA torch), generated by
`tools/deps/perception_groups.py`. After editing a requirements file:

```bash
just deps-lock        # regenerate the groups, then `uv lock` (keeps every version already locked)
```

and commit `perception/pyproject.toml` and `perception/uv.lock` with it. `tests/test_locks.py` fails while
either is out of date.

The same goes for the module lists: `BASE_MODULES` and `MTMC_MODULES` are read from the Dockerfile's `ARG` defaults
when the groups are generated, and recorded above each group (`# slim: BASE_MODULES="..."`). The image installs the
locked group, so a `--build-arg BASE_MODULES=...` (or `MTMC_MODULES`) could not change what it installs: a build whose
value differs from the recorded one stops at `install_locked.sh` with an error saying so. To change a list, edit the
default in `perception/pipeline/Dockerfile` and run `just deps-lock`.

## The root lock

`pyproject.toml` at the root is the source for the app, the tests, developer extras and the repo's tools, one group
each (the comments there say what each is for). `requirements.txt`, `requirements-test.txt` and
`requirements-dev.txt` are **exports**: the group's own requirements pinned to their locked versions, rewritten by
`tools/deps/root_exports.py`, for whatever still reads a requirements file (the app Dockerfile). Never edit them; change
the group, then `just deps-lock`. `tests/test_locks.py` fails while an export or the lock is stale.

Run something in a locked group without touching a project `.venv`:

```bash
uv run --locked --isolated --only-group test python -m pytest tests -q    # what `just check` and CI run
```

`--locked` refuses to run when `uv.lock` no longer matches `pyproject.toml` (instead of re-locking silently);
`--isolated` uses a throwaway environment; `--only-group` installs that group and nothing else. A plain `uv sync` at
the root installs the default groups (`app-image`, `test`) into `.venv`.

The exports pin only a group's direct requirements. The app image installs `requirements.txt` after CPU torch, then
InsightFace and onnxruntime; its Dockerfile pins those four to the lock's versions (`tests/test_locks.py` checks they
agree). Their transitive packages still float until the Dockerfile installs from the lock (see "Follow-ups").

## Compose images

Every third-party image is pinned as `name:version@sha256:<digest>`: the digest is what Docker runs, the version says
what it is. They are the builds that ran on the GPU server on 2026-11-03 (`deps/baseline/README.md`), not newer ones.
`tests/test_compose_pins.py` fails on an image without both. The images this repo builds itself (named from
variables, `...:latest`) are not covered.

The first `docker compose up` after this change recreates those containers once (their configuration names the image
differently); the image is the same, already local, and volumes are kept.

Three digests no longer have a tag pointing at them; the registry still serves them by digest, except MinIO:

- `minio/minio:RELEASE.2025-09-07T16-13-09Z`: Docker Hub refuses anonymous pulls of `minio/minio` (2026-11-03, 401 for
  every tag and digest). Only a machine that already has the image can start that service (see "Follow-ups").
- `node:22.23.2-slim` and `timescale/timescaledb-ha:pg16.15-ts2.30.2`: the tags were rebuilt after the builds that run
  here; the pins keep the running builds.

To update one: pick the new version tag, read its digest from the registry
(`docker buildx imagetools inspect <name>:<tag>`, or the tag's page on Docker Hub), and change both in the same line.

## CI

- `deps-locks` fails a merge request whose lock is stale: `uv lock --check` for all seven locks, plus the sidecar's
  groups against the requirements.txt files and the root's exports against its lock (`just check` runs the same).
- Every job installs with `uv sync --locked` (or `uv run --locked`): exactly the locked versions, hash-checked, and an
  error instead of a silent re-lock when the lock is stale. core-tests installs the root `test` group; barber,
  attendance (`attendance-service`: installs and imports the service) and fall_detection (`fall-detection-tests`) their
  own locks; the data jobs (`data-catalog`, `dvc-pointers`) the root `data` group (PyYAML only).

## Updates

Nothing updates on its own: every version change is a merge request, reviewed and tested like code.

**By hand**, one package at a time:

```bash
just deps-update fastapi                      # the root lock: newest version (within the pyproject range)
just deps-update insightface perception       # another lock: its directory
just deps-update 'pillow<13' perception       # newest within a bound, to stay in the current major
just deps-diff                                # what moved, per lock: MAJOR / minor / patch / added / removed / HELD
```

`deps-update` re-locks, rewrites the root's requirements exports and prints `deps-diff`. Review it like a code diff:
every line is a package that will run differently. A **MAJOR** or **HELD** line (torch, torchvision) is a deliberate
change in a merge request of its own, with a reason in its description. Then run the checks for what the lock serves:
`just check` (all of them), and for the sidecar's lock or image, a rebuild and the golden replay (below).

**Weekly, by Renovate** (`renovate.json5`): every Monday before 06:00 (Cairo) the bot opens at most one merge request
per group: the sidecar lock, the root lock, the tool locks, the product locks, and the images (Dockerfiles and compose).
Each runs the CPU suite and the lock checks in CI.

- **No majors.** Renovate's own rule skips major updates of direct dependencies and images. Lock-file maintenance
  (`uv lock --upgrade`) can still move a transitive package, or one of the sidecar's unversioned requirements, across a
  major (a dry run on 2026-11-03 would have moved insightface 1 -> 2, pillow 12 -> 13 and pycryptodome 3 -> 4), so after
  every update Renovate runs `tools/deps/hold_majors.py`, which re-locks each such package back to its version on the
  default branch and keeps every other update. CI's `deps-majors` job checks the result on Renovate's merge requests.
  "Major" is the first version number, or the first two for 0.x; calendar versions (2026.x) are not held.
  *Why not upper bounds in the pyprojects:* the sidecar's requirements.txt files are the source and stay unversioned,
  and bounds on some 400 transitive packages would be generated noise that Renovate would then propose to raise.
- **Held**: torch and torchvision (the sidecar's cuDNN workaround and the app Dockerfile's CPU pin depend on them), uv
  (moves everywhere at once), MinIO (no longer pullable), a new Python.
- **Approve first** on the Dependency Dashboard (the issue Renovate keeps open): timescaledb (the scale UI's database)
  and the DeepStream base image.
- **Golden replay: by hand, until #86 runs it in CI.** Before merging a sidecar lock or image update, rebuild the
  sidecar and run `tools/engine_golden_check.sh attendance zones fire multicam barber` on the GPU server (DATA.md, the
  golden groups). Each Renovate merge request says so in its description.
- **First run:** check that lock-file maintenance really opened one merge request per group (its branch prefix in
  `renovate.json5` is computed from each lock's directory; Renovate's documentation does not say how it splits them).

### Maintainer checklist (once, before the first run)

1. **A runner project** on gitlab.urca.ai (e.g. `iris/renovate-runner`) whose `.gitlab-ci.yml` is
   `deps/renovate-runner.gitlab-ci.yml`. Separate from this repository, so the bot's token never reaches its
   merge-request pipelines. Its runner needs a docker executor and access to ghcr.io, pypi.org,
   files.pythonhosted.org, download.pytorch.org, Docker Hub, nvcr.io and github.com.
2. **A bot token**: a project access token on `surveillance-camera-sys`, role Developer (Maintainer if protected
   branches must accept its pushes), scopes `api` and `write_repository`. Store it in the runner project as
   **`RENOVATE_TOKEN`** (masked, protected).
3. **Optional variables** in the runner project: `GITHUB_COM_TOKEN` (a read-only github.com token: release notes in the
   merge requests, and no anonymous rate limit), `RENOVATE_GIT_AUTHOR` (the bot's name and e-mail).
4. **A pipeline schedule** in the runner project: weekly, e.g. `0 3 * * 1` (Monday 03:00, Africa/Cairo), on its default
   branch. "Run pipeline" by hand works too.
5. In this repository: let the bot's merge requests run CI (no extra setting when the token is a project member), and
   keep `renovate.json5` on the default branch (the bot reads it from there).

## Rebuilding the images

The Dockerfiles use BuildKit features, so a build needs the **docker buildx plugin** (`docker buildx version`). Without
it the legacy builder is worse than failing: it **silently ignores `COPY --parents`** (checked: `a/b/f` lands at
`/src/f`), so the sidecar would build with its parser sources and requirements files flattened into one directory, a
different image. `verify_sidecar.sh` refuses to run without buildx.

On the GPU server, buildx **v0.38.1** is installed for the `iris2` user only (2026-11-04), no sudo, nothing
system-wide: the release binary `buildx-v0.38.1.linux-amd64` from github.com/docker/buildx/releases, checked against
the release's `checksums.txt` (sha256 `e25d5cd675092bb5d1d03632fdc46cdf3fede7b514dc5f023a105e00d3ce5ad4`), at
`~/.docker/cli-plugins/docker-buildx`. Another user needs the same in their own `~/.docker/cli-plugins/`. The default
builder is unchanged; `verify_sidecar.sh` uses a builder of its own.

Docker's data root on the GPU server is `/data/docker` (the `/data` disk), not `/`: builds and images use `/data`.

The sidecar installs from its lock (`perception/pipeline/install_locked.sh`: `uv export --frozen` of the target's
group, `uv pip install --require-hashes`, CUDA torch from the cu130 index, the GUI cv2 and the GPU ONNX Runtime last).
Its base image is pinned by digest and pyds by commit. The buffalo_l models are not in the image: the sidecar loads the
repo's DVC copy (perception/insightface_pack.py), pinned by sha256 in mtmc/tracking/imported_models.yaml
(tests/test_dockerfile_targets.py, tests/test_insightface_pack.py). To prove a rebuild is the image that runs today:

```bash
tools/deps/verify_sidecar.sh            # slim, then mtmc; `slim` or `mtmc` for one; --keep keeps the images
```

It builds with a builder of its own (removed at the end, with its cache; nobody else's cache is touched), refuses to
start when the Docker disk (`/data` on the GPU server) would drop under 15 GB (the peak is about 55 GB for slim and 20
GB more for mtmc), and checks: `uv pip freeze` against `deps/baseline/`, cv2 and ONNX Runtime from the right wheels, an
ONNX Runtime session on `CUDAExecutionProvider`, pyds, and for mtmc a CUDA op in torch. The checks pass on today's
running images (`km-deepstream-sidecar`, `scale-deepstream-sidecar`), so a rebuilt image that fails them differs. Then
the golden replay (Updates, above).

## Known gaps

- **apt packages** in the sidecar image (the build tools for pyds and the parsers, `libjbig0`) come from the Ubuntu
  archive at build time, unpinned. They only build pyds and the parsers; pinning them would need a dated snapshot
  mirror (snapshot.ubuntu.com).
